# AUTH CRYPTO — the three layers (decided 2026-08-31)

Signal protocol was considered and rejected: it solves asynchronous
messaging through an untrusted relay; this is two in-person-paired
devices on a direct interactive link carrying one bit. What shipped
instead:

## 1. Transport: BLE LE Secure Connections, no fallback

`CONFIG_BT_SMP_SC_PAIR_ONLY=y` — legacy pairing refused. Every GATT
characteristic is ENCRYPT-permission; bonds persist in the storage
partition (settings/NVS).

## 2. HMAC challenge-response

- Helper writes a fresh 16-byte nonce to the Challenge char before/while
  the user touches the knob.
- Module notifies Auth Result: `status(1) | slot(2,BE) | mac(32)` where
  `mac = HMAC-SHA256(K, nonce || status || slot_be16)`.
- All-zero mac = unauthenticated (no key provisioned or no fresh nonce);
  the helper MUST reject it for anything security-relevant.
- K is 32 bytes, generated by the helper at setup, written once to the
  Key char over the encrypted link, stored module-side in NVS (chosen
  over the sensor's Notepad pages: wear-leveled and readable at boot
  without powering the sensor rail).

Defeats: replay (fresh nonce), a spoofed peripheral or compromised BLE
stack (no K, no valid mac).

## 3. Hash ratchet

After each successful **authenticated OK** exchange, both ends step
`K = SHA-256(K)`. A K stolen today cannot forge or validate earlier
exchanges.

**Helper resync rule (must implement):** if a notify is lost after the
module ratcheted, the helper's verify fails with its current K — it
must retry verification with SHA-256(K) and, on success, adopt it.
One step only; two consecutive failures = treat as attack, not desync.
Module ratchets only after `bt_gatt_notify` returns success, keeping
the window at one step.

## Wire summary for the helper implementation
